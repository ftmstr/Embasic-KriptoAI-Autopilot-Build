## Actual external source investigation (not a proof issuance)

**GitHub job logs:** Official GitHub REST API `/repos/{owner}/{repo}/actions/jobs/{job_id}/logs` downloads ordinary logs via a temporary redirect. Public read access does not make those logs cryptographically signed entire-job attestations. Source: https://docs.github.com/en/rest/actions/workflow-jobs . The TUR54 Ubuntu and Windows workflow artifact collections were queried again and **both returned zero artifacts**; neither workflow contains an `actions/attest` step and existing permissions are `contents: read`. No independent provider-origin signature for whole original RAW job logs was obtained.

**GitHub artifact attestation:** Official GitHub workflow build attestations are about specific artifact subjects and require an `attest` step with `id-token: write` and `attestations: write` permissions. This is not equivalent to provider-signing the RAW original complete job log. Existing workflow permissions and path filters remain immutable by user instruction. Source: https://docs.github.com/en/actions/how-tos/secure-your-work/use-artifact-attestations/use-artifact-attestations ; https://github.com/actions/attest .

**Sigstore/Rekor:** An actual public transparency service exists. Rekor logs signed artifact metadata and supports independently verifiable Merkle inclusion/consistency. However merely pointing to the service, a claimed signed entry timestamp (SET promise), or even a log entry is **not** authorization of the owner/reviewer, not necessarily inclusion proof, and does not attest these GitHub raw job logs. External signed and independently witnessed root + inclusion + consistency + authorized signer identity would have to be obtained for this specific subject. Sources: https://docs.sigstore.dev/logging/overview/ and https://github.com/sigstore/architecture-docs/blob/main/rekor-spec.md .

**Remote CAS:** DynamoDB has conditional write capabilities, but its **MREC multi-region global tables** reconcile concurrent conflict via last-writer-wins; strongly consistent reads are not available cross-region. Therefore presenting MREC global tables as linearizable cross-region durable CAS is unacceptable. A separately administered, actually provisioned **single-region authoritative** conditional-write service with persistent fencing, restore policy and real multi-host tests may be a future pilot; none was provisioned or tested. Sources: https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/V2globaltables_HowItWorks.html and https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/globaltables_HowItWorks.html .

**Other four authority prerequisites:** No independent owner/reviewer OOB key custody/approval, trusted revocation time infrastructure, truly witnessed signed checkpoint for this subject, or recipient-authenticated idempotent remote ACK was supplied/available through the permitted repository access. 0 of 8 proof gates have genuine externally verified evidence.
